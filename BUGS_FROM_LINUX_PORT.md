# Bugs to fix in the next release — found by SD Core for Linux

Found 10 Sep 2026 while auditing SD Core for Linux against this port and adopting
its code. Each is a defect **in this (Windows) tree**. Linux fixed its own copy;
the fix below is what was done there — **except 5**, added 11 Sep, which Linux has
not built yet. Nothing here has been run on Windows.

| # | Where | Defect | Fix (as applied on Linux) |
|---|---|---|---|
| 1 | `sdsys/gpl.bp/MODIFYA`, `tier.build.rec` (under `voc.delta`) | **A tier downgrade removes nothing.** `tier.build.rec` still reduces field 1 (and a K record's field 3) to the type letter — the two lines PRE_RELEASE_FIXES 136 (2 Sep) removed from `CREATEA` and `LOGIN update.voc`, but not from here (it was written 27 Aug). Accounts now hold the whole description, so every rebuilt NEWVOC record compares unequal in `tier.del.one` and is counted "left alone" (10113's third number) instead of deleted: `modify.account x standard` leaves the PROGRAMMER verbs in place. | Drop the transformation in `tier.build.rec`; read the record whole from `newvoc`/`voc_template` exactly as `CREATEA` now writes it. (Linux: `GPL.BP/MODIFYA`, commit `8a1b343`.) |
| 2 | `gplsrc/sdtic.c`, `process_file()`, the `"Unexpected end of source file"` branch (`:537-539`) | **A truncated last entry still exits 0.** The branch does `goto exit_process_file`, which skips the `failed_entries++` UPSTREAM_FIXES 9 added, so a source whose final entry is cut short (e.g. its last line ends in a comma — the likeliest shape of a hand-edited `terminfo.mods`) reports success. | `failed_entries++;` before the `goto`. Witnessed on Linux: bad fixture, old sdtic 1 file / exit 0, fixed sdtic 2 files / exit 1 with the "did not compile" line. |
| 3 | `sdsys/messages/10114`, printed by `MODIFYA tier.set` when `voc.ok` is false | **The message can be false.** "Unable to change the tier of %1; nothing has changed" — but `voc.ok` also goes false in `tier.open.template` AFTER the standard layer may already have been applied (the banner there says so), so part of the VOC has changed. | Linux kept the port's text for conformity and recorded the objection. Suggested wording: "...; its tier in the register is unchanged". |
| 6 | `gpl.bp/DELETEF` DATA and DICT prompts (`:265-271`, and the DICT twin), messages 6135 / 6140 | **Two prompts missed by PRE_RELEASE 79, and they loop for ever at end of input** (added 11 Sep 2026). 79's inventory found prompts by their "Y/N" text; "OK to delete DATA portion '%1'?" has none, so it neither shows a default nor maps Enter. At end of input `input yn` yields '', which is neither Y nor N, and the `loop … until yn = 'Y' or yn = 'N'` re-asks with no escape — measured on Linux down a pipe: 98.9 MB of the question in 40 s. UPSTREAM 27's case-insensitive comparison makes the prompt rarer, not safe. Also undefaulted in the same shape: `CATALOG` 3033/3034/3035, DELETEF 6131, CPROC `.D` 5040 (Linux fixed these the same way, Enter = N); DELETEF 2050 and 6133 (not fixed on Linux — 2050's other five consumers treat anything but N as yes, and 6133's N still deletes the dictionary, so neither has an obviously safe default). `SPVIEW`'s prompt is fine: it presets Y in a formatted input field. | Messages 6135/6140 end "(y/<n>)? " and each loop gains `if yn = '' then yn = 'N'` before the `until` — N deletes nothing. (Linux: `GPL.BP/DELETEF`, 11 Sep, compiled, not yet run on an install.) |
| 7 | `gplsrc/op_lock.c` `op_getlocks()`, the two `UserPtr(abs(lock_owner))->username` (`:292`, `:312`) | **GETLOCKS / LIST.READU dereferences NULL for a lock whose owner's session is gone** (added 11 Sep 2026, measured on Linux). `UserPtr()` returns NULL for an unmapped user. On Linux it faulted inside the FILE_TABLE_LOCK + REC_LOCK_SEM section and left both held, which stopped every session. The Windows semaphores differ, so the consequence may too — the NULL does not. | A helper returning "(gone)" when `UserPtr()` is NULL, used at both sites. (Linux, 11 Sep, built, not yet run.) |
| 4 | `sdsys/gpl.bp/CREATEA`, `START-DESCRIPTION` | **Stale grammar in the header**: `CREATE.ACCOUNT account.name path.name [NO.QUERY]`, the pre-0.9.0 form. A Linux session copied the equivalent line into a user-facing message and shipped a command that fails. The syntax the verb prints is right; the comment is not. | Replace the block with the grammar the verb actually accepts. |
| 5 | §5.12, lower case — `gpl.bp/CREATEF:309-311`, `gpl.bp/LOGIN:624`, `syscom/KEYS.H:269`, all of `gpl.bp` and `syscom`, `newvoc`/`voc_template` | ***THE LOWER-CASE CONVERSION IS INCOMPLETE*** (added 11 Sep 2026; owner's ruling). The standard was meant to be **everything lower case, with upper-case input converted on the fly, so that no command, file or record id can exist in two casings**. It was only partly done; NTFS matches names regardless of case, so what was missed never failed here. Measured on this tree 11 Sep: `CREATE.FILE` still upper-cases the OS name of every new file unless the `CREATE.FILE.CASE` option is set, and nothing sets it (`CREATEF:311`); all 203 `gpl.bp` program sources and 12 of 15 `syscom` includes are upper case; `LOGIN:624` still sets `pterm(PT$INVERT, @true)`; account names are "forced to uppercase" (`KEYS.H:269`); `$ACC`, `$MAP`, `$RELEASE`, `SD.VOCLIB` and both `TIER.*` records are upper-case VOC ids. The lookup fold tries as typed, then lower, then upper, so an upper-case name keeps working instead of being brought into line, and nothing stops the same name existing in two casings — in a VOC or other hashed file the record ids `LIST` and `list` are two different records. (`%E`/`%G`/`%L` are escaped filenames, not names, and are correct as they are.) | **Not yet fixed on Linux** — it is Linux's §M, release-blocking, and there it must be complete because ext4 is case-sensitive. Intended there: every name SD ships or creates is lower case, including new files and program/include names; input is folded to lower on the fly; and SD refuses, naming both paths, if it finds the same name in two casings. Whether this reaches record ids in users' own data files and account names is not yet ruled. |

Also worth knowing (not bugs here): Linux renumbered its Linux-only kernel keys to
90+ and Linux-only messages to 10900+ so the two systems' numbers never mean
different things. Please keep 90–99 and 10900–10999 free in this port.
